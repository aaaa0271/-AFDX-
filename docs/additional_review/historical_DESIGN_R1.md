# R1 设计说明

## 1. 顶层与数据流

`AFDX_competition_top` 是唯一联合顶层。应用写入 → 端口/SAP 查找及静态配置 → 各 Sub-VL 完整消息存储 → 逐帧/分片轮询 → VL 级 BAG/序号 → 业务帧，与 SNMP、加载/RTC 帧共同进入帧原子仲裁 → A/B 物理 MAC 字节口。

输入 A/B 字节先做帧格式/FCS 检查。业务路径按配置的目标 MAC、IP、UDP、LMAX 分类，经过每 VL 的序号/冗余处理，再进入对应端口的重组/消息队列。管理和服务路径有独立的校验/分发，再交由 SNMP、TFTP/加载和 RTC。应用不读取未完成/未验证的重组缓冲。

## 2. 四 VL × 四 Sub-VL

端口索引为 `{subvl[1:0], vl[1:0]}`。每 VL 的序号、IP ID 分配和 BAG 仍只有一个上下文，不因多一个 Sub-VL 就重新计数。调度在两个层次做轮询：可发送 VL 之间轮询；选定 VL 的非空 Sub-VL 之间每次取一个完整 MAC 帧或 IP 分片。长队列消息分片后不会独占该 VL，短采样消息能在后续 BAG 获得发送机会。

每排队端口有两个完成消息槽。同周期入队/出队联合更新计数和指针，不覆盖其中一个事件。采样模式采用三个物理存储槽，使待发送/读取的活动事务和最新发布值分离。新值不会修改正在输出的报文或正在背压等待的应用读取。

默认基本四端口支持 8192 字节消息，新增十二端口支持 2048 字节，可配置扩大。接收前检查偏移+分片长度与该端口容量，禁止跨缓冲写入。配置冲突、未知 SAP、无权限分区、超容量、队列满均在接口边界拒绝或施加背压。

## 3. 静态配置与应用接口

VL 表控制网络地址和 LMAX；端口表控制 UDP 覆盖、采样/排队、SAP ID 和本地分区访问位图。完成配置后统一 seal，运行中的改写产生错误且不修改原表。重新配置需要复位/重新初始化，而不是在一帧中途切换策略。

写入接口使用 ready/accept 字节握手，并核对 SOF/EOF 与声明长度；输入元数据应在完整消息期间保持稳定。显式读取模式按 VL/Sub-VL/分区发起请求，payload ready 可以暂停读取。采样读取不消耗最新值，freshness 在开始读取时锁定；排队读取按 FIFO 顺序消费。自动读取模式保留传统四 VL 接口行为，是应用聚合接口，不作为隔离分区的读取 API。

## 4. 管理、加载和时钟

SNMPv2c BER 解析、请求关联、原子快照和响应构造均在 RTL 中。独立 PySNMP 解码实际响应，并与快照记录和线字节相互核对。R1 是只读私有遥测 MIB，不冒充 MIB-II/IF-MIB 全实现。私有统计主要来自业务核心；顶层物理总帧计数另有输出，不把业务计数称为标准 IF-MIB 总计数。

加载流程由目标端 TFTP 控制服务器、A4 上传控制器、LUH 解析器、数据文件抓取器和状态报告器协作完成。先检查头与硬件标识、文件长度/CRC，再在非活动 bank 准备文件；最终 LUS 被 ACK 后才能原子提交。失败、重试耗尽或校验错误不能改变旧活动镜像。该流程是有界上传子集，information/download 等完整过程不是 R1 的完成声明。

RTC 使用 NTPv4 格式请求/响应，验证服务器地址、端口、模式、层级、origin 关联和时间戳关系。UTC 可以校正，单调计数不倒退。独立逻辑参考时钟验证偏移、漂移、失步和恢复；不是完整 NTP 守护进程算法组实现。

## 5. 完整性和隔离

- Ethernet FCS、IP 头和非零 UDP 校验和验证失败不提交应用数据。
- A/B source Interface_ID 重写后重新计算 FCS，但不能把上游故障注入的坏帧“修复”为好帧。
- 每 VL 的序号/去重仍与各通信端口分开，不把 Sub-VL 当作新的 VL 序号域。
- 端口队列隔离，采样替换不污染其它端口，读事务被背压时元数据和数据保持。
- 多端口模式在首片之前无法确定端口的模糊孤儿分片会丢弃，不猜测目标 SAP。传统单端口/VL 的乱序用例继续保留。此边界不被隐藏为完整 RFC 重组能力。
